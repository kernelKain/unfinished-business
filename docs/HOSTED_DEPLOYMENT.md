# Hosted deployment

There are two hosted modes. They share the same application, but they differ in who owns the OpenCode connection and credentials.

| Mode | `UB_DEPLOYMENT_MODE` | Connection editing | Provider credentials |
|---|---|---|---|
| Local | `local` (default outside Render) | Wizard enabled | OpenCode's local credential store |
| Private hosted | `hosted-private` | Read-only; environment/secret store | OpenCode's persistent XDG data and the deployment's secret store |
| Public demo | `hosted-demo` | Read-only; environment/secret store | Must not ask visitors for provider keys; may have no models |

`RENDER` defaults the mode to `hosted-private` unless `UB_DEPLOYMENT_MODE` is set explicitly. The existing password-protected Render service is a private hosted deployment, not a public demo.

## Private hosted deployment

The deployment owns the OpenCode process and its credentials. Visitors never supply provider keys and do not need to know the OpenCode server password.

### Environment

Required or recommended:

```dotenv
UB_DEPLOYMENT_MODE=hosted-private
UB_HOST=0.0.0.0
UB_DATA_DIR=/var/data/unfinished-business
UB_ACCESS_USERNAME=unfinished-business
UB_ACCESS_PASSWORD=generated-by-the-platform
UB_SESSION_TOKEN=generated-by-the-platform

OPENCODE_BASE_URL=http://127.0.0.1:4096
OPENCODE_PASSWORD=generated-by-the-platform
OPENCODE_DATA_HOME=/var/data/xdg-data
OPENCODE_CONFIG_HOME=/var/data/xdg-config
```

- `UB_ACCESS_PASSWORD` protects the whole hosted app with HTTP Basic auth. `/api/health` remains public for the platform health check.
- `OPENCODE_PASSWORD` is the Basic-auth password for the loopback OpenCode server. The render start script starts OpenCode with the same value.
- `OPENCODE_DATA_HOME` and `OPENCODE_CONFIG_HOME` must be on the persistent disk. Provider accounts, model catalogs, sessions, and OpenCode's own credential store live there.
- `UB_SESSION_TOKEN` gates browser mutations. On Render it is generated by the platform.
- The app's `connection.json` contains only the URL/auth metadata, never the password.

### Provider credentials

Connect providers inside OpenCode once, using `/connect` in the server's environment (or configure the supported provider environment variables on the OpenCode process). The workshop discovers the resulting catalog. Do not add `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or similar keys to the application's environment for the purpose of forwarding them; the application has no code path that reads or returns them.

If the deployment needs a credential that OpenCode cannot resolve from its own store, put it in the OpenCode process environment or its config, not in the workshop.

### Start OpenCode and the app

`render.yaml` uses `npm run start:render`, which:

1. requires `OPENCODE_PASSWORD`;
2. starts the pinned OpenCode binary on `127.0.0.1:4096`;
3. starts the application server and its persistent project store;
4. stops both on `SIGTERM`/`SIGINT`.

The Render build runs `npm ci && npm run typecheck && npm test && npm run build` and uses `/api/health` for its health check. The service needs a persistent disk because project state, the demo workspace, and OpenCode's XDG data are all written under `/var/data`.

### Hosted connection UI

In `hosted-private` mode the wizard is read-only:

- The URL and password fields are disabled.
- `POST /api/connection/configure` returns `409 CONNECTION_MANAGED`.
- The panel still shows precise diagnostics and can retry the managed connection.
- The model chooser still works against the discovered catalog, and the chosen model is stored per project.

The operator repairs a broken connection through deployment environment/secret updates and a restart, not through the browser.

## Public demo restrictions

A public demo must not ask visitors for provider API keys or OpenCode passwords. That is true even if the demo is read-only in other respects.

Required posture:

- `UB_DEPLOYMENT_MODE=hosted-demo`.
- Connection configuration is read-only; the browser cannot change the URL or auth secret.
- No provider-key field exists in the UI or API.
- No provider credentials are copied into browser storage, project JSON, logs, events, Sentry, or exports.
- If no provider is connected, the demo shows `NO_MODELS` with a link to the OpenCode setup documentation and does not request a key.
- The public demo should not expose a shared workspace where visitors can execute arbitrary commands. If execution is enabled, use an isolated workspace, explicit Maker scope, and the same permission denials as local mode.

A public demo may use free catalog models that OpenCode exposes without a visitor credential. It must not present a paid model as free or imply that quota is available.

## Security policy

- Remote OpenCode URLs require HTTPS. The API rejects `http://` for anything other than `localhost`, `127.0.0.1`, or `::1`.
- Credentials in the server URL are rejected.
- The application connects to OpenCode from its own process. It does not proxy provider traffic from the browser, so browser CORS is not a path to the OpenCode API.
- Session actions are limited to sessions referenced by the active project.
- The application never accepts provider keys. Unknown credential-shaped fields are rejected.
- Logs and Sentry events must not include passwords, authorization headers, provider keys, or raw session prompt bodies.
- Source maps and Sentry release uploads do not change any of these boundaries.

## Rollback and recovery

- If the OpenCode server is unreachable, the app reports `unavailable` and leaves project state intact.
- If the process restarts while a run is in flight, the operation is preserved as `UNKNOWN` for explicit reconciliation. It is not replayed.
- If the managed connection password changes, update `OPENCODE_PASSWORD` and restart both processes. The in-memory password is not persisted across a restart.
- A corrupt `project.json` is preserved while a previous snapshot is offered; the app does not silently reset the project.

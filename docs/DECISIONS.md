| ID | Decision | Alternatives considered | Rationale | Consequence |

| D8-01 | Use one canonical `UB_DEPLOYMENT_MODE` (`local`, `hosted-demo`, `private-hosted`) | Keep parallel `UB_MODE` values | Two mode dialects caused contradictory docs and startup behavior | Legacy alias accepted; `hosted-private` and `private-hosted` map to the same mode |
| D8-02 | Make hosted-demo public and read-only, not password-protected | Reuse the private Basic Auth path for the demo | The demo contains no user data, secret, engine, or mutation; requiring credentials would make the judge path worse | No token, no OpenCode, every non-GET `/api/*` → `DEMO_READ_ONLY` |

## Upgrade Phase 2 — observable, cancellable, recoverable runs

| ID | Decision | Alternatives considered | Rationale | Consequence |
|---|---|---|---|---|
| U2-01 | Consume the OpenCode event/session APIs, then choose safe polling for live progress | Subscribe to the SSE event stream (`client.event.subscribe`) inside the run coordinator | The installed client (`@opencode/client` 2.0.32) exposes a shared SSE stream plus `message.list`, `session.get`, `session.diff`, and permission endpoints; Unfinished Business routes every native call through a capped, policy-checked `fetch` (`maxResponseBytes`, timeouts, SSRF guards) that is built for bounded responses, not unbounded streams | Progress phases are observed via the same bounded APIs already used for runs; the SSE path is documented as the future upgrade, not silently used |
| U2-02 | Persist all four spirit runs as asynchronous operations; keep `question` synchronous | Make every `sendMessage` intent async; keep Oracle/Architect/Witness synchronous with cancel polling | Stage runs change saved state and need progress/recovery; a question changes nothing and answers directly, so its frozen-request risk is low | `clarify`/`draft`/`witness` and Maker return `202` with a queued operation; `question` remains a direct response, documented |
| U2-03 | Record a fixed phase vocabulary and never stream raw model text into it | Stream partial model output (labeled) into the document | Partial output invites pasting unvalidated text into approvals, and labels do not make raw streams safe to save | Phases are safe summaries only; partial output is never displayed, and sections are stored only from validated, complete replies |
| U2-04 | Recovery metadata per operation: intent, sectionId, startingRevision, idempotency key, expected output, retry lineage, progress | Recompute intent from the transcript; reconcile by hash only | Reconciliation must know exactly what to apply, to which section, against what expected output — without guessing from strings | `intent`, `sectionId`, `startingRevision`, `idempotencyKey`, `expectedOutput`, `retryOf`, and `progress` are persisted and migrate forward |
| U2-05 | Reconcile retrieves and validates the actual late response or diff, then applies at most once | Trust `session.outcome`/idle as success; keep the outcome-only reconcile of Phase 1 | An idle session is not a validated result; guide replies must re-parse against the same schemas and Maker diffs must be re-read and re-checked | `appliedAt` plus the idempotent action record makes repeated reconciliation inert; `COMPLETED_UNAPPLIED` is reachable when the result exists but is not yet readable |
| U2-06 | Restrict retry-after-failure to confirmed `FAILED` Maker runs; retries create a new operation with `retryOf` lineage | Retry ABANDONED runs; reuse the same operation id for retries | Retrying an uncertain run can duplicate a native edit that may still land; a new id keeps history intact, and only Maker runs persist a replayable scope | `POST /api/runs/:id/retry` refuses non-Maker, unresolved, and already-active runs; guide retries remain explicit new requests from the panel |
| U2-07 | Migration backfills migrated non-terminal operations with a deterministic `AWAITING_RECONCILIATION` marker | Leave progress empty for migrated rows | Old unknown operations must remain recoverable through migration, and the interface has to explain that honestly | v1/v2/v3/v4 sources migrate to v5 with the sentinel-stamped recovery marker; terminal rows keep no progress marker |
| U2-08 | Keep the Run Inspector's recovery controls out of the deterministic demo rendering | Show identical controls on the demo | The demo is a fixture with no live session; live elapsed timers in snapshot tests would make captures nondeterministic | Demo captures stay byte-stable; the workshop exposes Continue waiting / Reconcile now / Open in OpenCode / Cancel / Retry / Mark abandoned |

## Upgrade Phase 3 — project intake and guided discovery

| ID | Decision | Alternatives considered | Rationale | Consequence |
|---|---|---|---|---|
| U3-01 | Require an explicit project source before Oracle can run | Infer source from free text; default silently to a blank project | Repository trust and discovery questions differ materially across new, local, remote, and saved work | Fresh projects begin `UNSELECTED`; the source panel is the first workshop step and the server returns `PROJECT_SOURCE_REQUIRED` if bypassed |
| U3-02 | Treat remote selection and remote import as two separate actions | Clone immediately when a URL is entered; let OpenCode work in the clone without confirmation | URL validation is not consent to create a checkout or grant an agent a writable workspace | Selection stores a credential-free public HTTPS URL and managed target as `PENDING_CONFIRMATION`; only the confirm route imports and marks it `CONFIRMED` |
| U3-03 | Reuse canonical workspace-security rules for local repositories and keep paths private | Accept arbitrary strings; expose the selected path to Oracle for context | Symlink/broad-root policy already defines the safe local boundary, while an absolute path is not useful product context | Local paths are canonicalized without creating them, stored only in private state, and omitted from API responses and prompts |
| U3-04 | Keep the complete Product Discovery prompt and append a persistence adapter | Replace the runtime procedure with a short one-shot JSON prompt | Oracle still needs the full interviewing method; JSON is a storage contract, not the product behavior | Prompt 0 remains first and intact; a detailed adapter requests the richer schema and current structured memory |
| U3-05 | Limit each Oracle turn to two or three high-value questions with rationale and optional choices | Ask the entire intake form; allow an unbounded question array | Short turns are easier to answer and make the reason for each question visible | The reply schema caps questions at three and requires `whyItMatters`; suggested choices remain optional |
| U3-06 | Enforce proposal sufficiency on the server | Trust the model's `mode`; generate a placeholder proposal after one turn | A schema-valid shallow proposal can still omit essential context | Source confirmation plus intended user, problem, desired outcome, and must-have features are required; assumed essential fields additionally require the user's explicit proceed-with-assumptions action |
| U3-07 | Store field-level answers and assumptions with provenance; supersede corrections | Preserve only the raw transcript; mutate an old memory entry in place | Reloads and corrections need a durable distinction among facts, user decisions, and assumptions | Active memory drives prompts and UI; corrections create a new active entry and mark the prior entry `SUPERSEDED` |
| U3-08 | Migrate every v1–v5 project explicitly to schema v6 | Reset old Oracle state; make v5 the minimum supported version | Existing projects, approvals, run recovery, and transcripts must remain usable | Legacy projects become confirmed saved work, old Oracle summaries/questions are retained in structured intake, and repeated migration remains deterministic |
| U3-09 | Import only public, credential-free HTTPS repositories with a noninteractive Git subprocess | Accept SSH/private URLs; rely on ambient credential helpers; show clone output | Embedded/ambient credentials and raw Git errors could leak secrets, and redirects can change the trust boundary | Userinfo/query/fragment/nonstandard ports/private DNS are rejected; credential helpers, prompts, and redirects are disabled; output is discarded and failures use a fixed safe message |

## Upgrade Phase 4 — reviewable generated revisions

| ID | Decision | Alternatives considered | Rationale | Consequence |
|---|---|---|---|---|
| U4-01 | Validate every Architect candidate against a section-specific content contract | Trust the model; enforce a minimum word count | Word count rewards padding and does not prove that a plan covers its dependencies, risks, decisions, or acceptance criteria | Each of the eight sections declares required topics, detail guidance, dependencies, risk/decision requirements, acceptance criteria, and required headings; validation is structural and topic-based |
| U4-02 | Generate a `PENDING` candidate instead of replacing the draft | Apply the Architect reply immediately and mark downstream stale | The user must be able to inspect the complete revision before it replaces approved or draft work | `POST /api/sections/:id/revisions` queues the Architect; the current section is untouched until an explicit accept |
| U4-03 | Require an explicit accept/reject decision and bind it to the candidate base version/hash | Accept by latest content; auto-accept if the contract passes | A section can change while a candidate is being reviewed; silent overwrite is unacceptable | Accept fails with a conflict if the base changed; the user can request a fresh candidate or discard the old one |
| U4-04 | Keep acceptance separate from approval | Treat accepting a revision as approval | The user may accept wording but still want a separate approval gate; approvals are exact-version security boundaries | Accepting sets the section to `DRAFT` at the candidate version; `approveSection` remains the only path to `APPROVED` |
| U4-05 | Mark the accepted section's approval and every transitive dependent approval stale | Mark all sections stale; leave downstream approvals untouched | Only sections whose inputs changed need review; unrelated approvals should stay valid | The accepted section becomes `DRAFT`; dependent `APPROVED` sections become `STALE` and their approvals record the upstream change |
| U4-06 | Render a safe Markdown subset with React text nodes and filtered links | `dangerouslySetInnerHTML`; a permissive Markdown/HTML pipeline | Generated content is untrusted model output; raw HTML and `javascript:` links must never execute | Headings, paragraphs, lists, emphasis, links, tables, and code render without HTML injection; unsafe links are reduced to their labels |
| U4-07 | Use a shared line diff for unified and side-by-side views, defaulting by screen width | Separate diff implementations; always side-by-side | Both views must describe the same change, and narrow screens cannot show two readable columns | One LCS diff feeds both views; side-by-side is the wide default and stacks with labels on narrow screens |
| U4-08 | Migrate v1–v6 projects explicitly to schema v7 | Reset candidates; keep v6 and silently default new fields | Existing projects and audit history must remain usable | Legacy candidates gain deterministic base/summary/decision defaults; no IDs or timestamps are invented |
